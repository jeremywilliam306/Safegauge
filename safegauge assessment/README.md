# SafeGauge Portal — take-home submission

## Running it
ensure npm is installed with the latest version
npm install
npm run dev   → http://localhost:5173

Demo accounts:
- admin / safegauge (has full access)


## What's done
**Auth Login Form**
- Auth: login form which has an inline error on bad credentials, logout button which calls Api.logout to indavlidate the token. Implemented a global 401 handling (apiClient.js) wraps every Api call so a dead token anywhere in the app routes back to login automatically.
- Session persistance is also implemented so that token and user are saved into the localStorage which would be revalidated by Api.me(). However, it would not survive from a refresh

**Devices with CRUD**
- Devices: list, create, delete and edit is built
- Under create new DeviceList, entries appear without re-fetching the whole list
- in api.Client.js, it wraps all the 5 operations of CRUD
- The create and edit shares one form of component that pre-fills
when editing
- 422 validation errors from the server show up right under a specific field of input
- Deleting a device removes it from the list instantly without confirmation 

**Live Dashboard**
- Clicking a device connects to sensorHub and shows a live grid of the sensors id, type, current value, and its unit, constantly updating.
- The dashboard shows status on whether device is connected/reconnecting or disconnected.
- Switching to a different device disconnects the old connection and clears the reading. The new connection would generate a new metric. No stale data left over.

**CSS Basic Styling**
- I passed a light CSS for the HTML to have some structure. This is mainly for the card layout, the grids on sensor tiles, and a highlighted active tab.

**Alert Rules**
- For a selected device, you are able to list, add, or delete a rule
- Live dashboard and the Alert rules are seperated under 2 tabs for a selected device.
- The sensor dropdown dashboard offers ids that exist in the number of sensors in a given device. So 5 sensors would display 5 cards.

## Trade-offs / known issues

- Refreshing the page would log you out, but to keep someone logged in after a refresh (save the session, re-check it with the API when the page loads). Reading mock-api.js's actual source, it never saves login tokens anywhere permanent, so I made every token becoming invalid the instant the page reloads
- Didnt implement on Devices for `firmwareVersion` to tell you what version the soft is running on. Also for `subscribeAll` and `calibrationId` method on sensor-sdk.min.js
- I also did not implement Api.rules.bulkCreate from the mock-api.js since i did not want to break any placeholders that would be left out in the UI
- The DeviceForm just sends whatever's typed and lets the server say what's wrong (empty name, sensor count out of range, etc.), then shows those errors. I didn't duplicate that checking logic in the browser too.
- Sensor ids for the rules in the sensor.js was generated by Claude. The sensor-sdk did not specify the way to list a device sensor ids. Which then i generated a helper to produce the formula so that the dropdowns could offer a valid ids that matches with what the device will actually report.
- When new devices are created, i add them straight to the exisiting list in memory, not through calling the list endpoint. But if 2 users are viewing them together, they could end up seeing different variable lists.
